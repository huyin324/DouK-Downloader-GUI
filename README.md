# DouK-Downloader GUI

基于 **Python + PyQt6** 的图形界面外壳，内核为
[DouK-Downloader V5.8](https://github.com/JoeanAmier/TikTokDownloader)（抖音 / TikTok 作品下载与数据采集工具）。

> **设计原则：内核源码零改动。**
> 上游 `upstream/` 目录保持与原仓库完全一致，所有界面化改造、去重优化与反爬虫增强
> 均通过运行时包装实现，可随时关闭并完全回退到内核的原始行为。

---

## 一、需求实现对照

| # | 需求 | 实现位置 | 说明 |
| --- | --- | --- | --- |
| 1 | 做成图形界面（Python + PyQt6），**原有下载逻辑不变** | `run.py` + `app/` | 上游 `upstream/` 一个字节未改（`git status` 校验通过）；GUI 完全通过运行时包装驱动内核 |
| 2 | 全部参数图形化；左半屏设置项、右半屏日志 | `app/settings_panel.py`、`app/log_panel.py`、`app/main_window.py` | 左右 1:1 分栏；覆盖内核 `settings.json` 的全部 38 个键 |
| 3 | 每项旁有 `?` 图标，点击显示描述与示例；参数持久化 | `app/widgets.py`、`app/field_spec.py`、`app/config_store.py` | 每个参数都有独立说明弹窗（功能说明 + 示例 + 可选值 + 取值范围）；配置写入 `config/gui_settings.json` |
| 4 | 在原有去重逻辑上优化，已下载资源跳过以节省时间与带宽 | `app/dedup.py` + `app/engine.py` | 把去重判断**提前到请求之前**；实测 30,172 条记录过滤仅需 113 ms，且重复任务媒体请求降为 0 |
| 5 | 在原有反爬逻辑上优化，增强反爬虫性能 | `app/antispider.py` | 请求节流 / 指纹轮换 / 指数退避 / 并发控制 / 批次休眠，全部可配置且可一键关闭 |
| 6 | 分抖音与 TikTok 两页；每页首行 Cookie → 下载类型 → 链接传入方式（粘贴 / 本地 txt） | `app/settings_panel.py` | 单个分页内严格按此顺序排列，见第五节 |

## 二、快速开始

### 方式 A：下载打包好的 exe（推荐，无需安装 Python）

到 [Releases](../../releases) 下载 `DouK-Downloader-GUI.exe`，双击运行即可。
配置、下载记录数据库与日志都保存在 exe 所在目录。

### 方式 B：从源码运行

```bash
# 0. 克隆（upstream/ 是上游内核的 git submodule，务必带 --recursive）
git clone --recursive https://github.com/huyin324/DouK-Downloader-GUI.git
cd DouK-Downloader-GUI

# 1. 创建虚拟环境（需 Python 3.12 及以上）
python -m venv .venv

# 2. 安装依赖
.venv\Scripts\python.exe -m pip install -r requirements.txt

# 3. 启动
.venv\Scripts\python.exe run.py
```

也可以直接双击 `启动.bat`（会自动优先使用 `.venv`）。

**首次使用请先填写 Cookie**：在左侧对应分页的第一行填入 Cookie，
点击旁边的「校验登录状态」确认已登录后再开始任务。
Cookie 获取方法见内核文档的
[Cookie 获取教程](https://github.com/JoeanAmier/TikTokDownloader/blob/master/docs/Cookie%E8%8E%B7%E5%8F%96%E6%95%99%E7%A8%8B.md)。

### 从命令行版本迁移

如果你之前用命令行版内核下载过作品，可以两种方式复用已有成果：

1. **复用下载记录（推荐，直接让去重生效）**
   点击工具栏的「**导入下载记录**」，选择旧安装目录下的
   `Volume\DouK-Downloader.db`
   （例如 `TikTokDownloader_V5.7_Windows_X64\_internal\Volume\DouK-Downloader.db`）。
   程序会：

   - 合并 `download_data`（已下载作品 ID）与 `mapping_data`（昵称缓存）；
   - 采用 `INSERT OR IGNORE`，**只增不覆盖**，可反复执行；
   - 写入前自动把目标库备份到 `.workbuddy/backup/`；
   - 完成后做 `PRAGMA integrity_check` 与行数校验。

   也可以用命令行完成同样的事：

   ```bash
   .venv\Scripts\python.exe import_legacy_records.py
   .venv\Scripts\python.exe import_legacy_records.py --inspect      # 只看不写
   .venv\Scripts\python.exe import_legacy_records.py --source "D:\old\Volume\DouK-Downloader.db"
   ```

   导入后「下载前预过滤」会直接跳过这些作品，不再消耗任何接口请求。

2. **复用参数与 Cookie**
   点击工具栏的「导入内核配置」，选择旧的 `settings.json`，
   程序会自动导入 Cookie 与各项参数。

   > 注意：旧配置里的「保存根目录」可能来自 macOS 或其他电脑
   > （例如 `/Volumes/Data/...`、`Z:\...`），导入后请改成当前系统的有效路径，
   > 否则内核会回退到默认目录。

   > Cookie 支持两种格式：浏览器复制的 `k=v; k=v` 原始串，
   > 以及内核旧配置里的 JSON 对象 `{"k": "v"}`，程序会自动转换。

### 4.2 每个分页的排列顺序（需求 6）

严格按需求组织，自上而下为：

1. **Cookie**（首行）—— 附带「从剪贴板粘贴」「校验登录状态」「清空」
2. **下载类型** —— 批量下载链接作品 / 账号作品 / 合集作品 / 获取直播拉流地址
3. **链接传入方式** —— 粘贴链接 或 从本地 txt 文本读取（附「解析文件内容」）
4. **下载内容** —— 音乐、静态封面、动态封面、原画质量、独立文件夹
5. **文件命名与保存位置**
6. **网络请求** —— 超时、重试、分块、体积上限、代理、翻页上限
7. **反爬虫增强**
8. **去重优化**
9. **平台开关**
10. **高级设置** —— FFmpeg、直播清晰度、浏览器指纹

两个分页共享「通用」参数：切换分页时会自动同步，不会出现两页数值不一致。

任务模式与链接来源还会联动：选择「账号作品」才显示账号作品类型；
选择「txt 文件」时粘贴框自动隐藏。

### 4.4 文件名参考预览

「文件命名与保存位置」板块在「文件名组成」下方有一行**实时生成的参考文件名**：
勾选元素、切换分隔符、修改长度或时间格式时立即刷新，可直接选中复制用于提前核对。

算法与内核完全一致，并已用上游真实的 `Cleaner` / `beautify_string` 逐例对照验证
（`tests/feature_test.py`）：

1. 先按「描述最大长度」截断作品描述；
2. 按「文件名组成」的勾选顺序用「文件名分隔符」拼接；
3. 经 `filter_name` 清洗 —— **`:` 会被替换为 `.`**（所以时间是 `10.22.46` 而非 `10:22:46`），
   并移除 Windows 非法字符、控制字符、emoji，折叠连续空格；
4. 再按「文件名最大长度」整体截断（超长时保留首尾并加 `...`）；
5. 清洗后为空时回退为作品 ID。

示例（勾选 发布时间 + 作品类型 + 账号昵称 + 作品描述，分隔符 `-`）：

```
2026-09-17 10.22.46-视频-某某某-今天天气不错.mp4
```

> 参考文件名里的时间是**当前时刻**，其余为示例值；扩展名按作品类型给出常规取值，
> 真实扩展名由响应头的 `Content-Type` 决定。
> 勾选「自定义标记」时会有提示：该段只在该账号配置里填写过标记时才有值。

### 4.6 下载类型与链接类型必须匹配

四种下载类型各自只处理一种链接，选错会白跑一轮且最终报「未能解析出任何作品 ID」：

| 下载类型 | 能识别的链接 | 例子 |
| --- | --- | --- |
| 批量下载链接作品 | **作品链接**（URL 里含 19 位作品 ID） | `douyin.com/video/7300000000000000000` |
| 批量下载账号作品 | **账号主页链接** | `douyin.com/user/MS4wLjABAAAA…` |
| 批量下载合集作品 | **合集链接**（或合集内任意作品链接） | `douyin.com/collection/7300000000000000000` |
| 获取直播拉流地址 | **直播链接** | `live.douyin.com/123456` |

程序在**启动前**会自动识别链接类型；若与所选下载类型明显不匹配（某类占比 ≥60%），
会弹出提示并给出改选建议，可直接一键切换到推荐类型：

```
共 110 条输入：账号主页链接 110 条。

当前下载类型是「批量下载链接作品」，但输入主要是账号主页链接，
该模式不会处理这类链接，最终只会提示「未能解析出任何作品 ID」。

建议改用「批量下载账号作品」。
```

> 为什么这点很重要：内核解析链接时会对**每条短链**发一次请求并按反爬间隔等待。
> 113 条链接若逐条请求，实测要跑 **12 分钟**才轮到报错。
> 因此本项目还做了两件事：
> 1. **只有短链才发请求** —— 完整链接里的作品 ID 可直接正则提取，实测省下 110 次请求，
>    同一批输入从 **12 分 14 秒降到 1.6 秒**；
> 2. 短链解析阶段输出**进度与预计耗时**，并可随时「停止」，不再长时间无反馈。

### 4.7 实时计数栏

进度条左侧显示账号进度（固定宽度），下方一行按文件类型汇总本次任务的实时进度，运行中逐条刷新：

```
账号数量 3/110   [━━━━━━ 进度条 ━━━━━━]

视频：12 | 8 │ 图集：5 | 3 │ 实况：1 | 0 │ 音乐：2 | 0 │ 封面：4 | 1 │ 动图：0 | 0
```

- 每项形如 `类型：下载数 | 跳过数`，**绿色为已下载数、红色为跳过数**；全为 0 的类型显示为灰色。
- 类型项按内容紧凑排布（各项等宽，不随窗口拉伸）。
- 数据来源两条互补：
  - **内核日志** —— 每完成或跳过一个文件都会打印带类型前缀的消息
    （`【视频】… 文件下载成功`、`【图集】…_2 文件已存在，跳过下载`），
    由此可覆盖内核自身统计不到的**音乐 / 封面 / 动图**；
  - **引擎自身计数** —— 处理的账号数等。
- 另外单独统计**体积超限跳过**与**下载地址提取失败**（仅在日志汇总中体现），便于区分"跳过原因"。
- 任务结束时日志里还会汇总解析出的作品数与去重预过滤跳过数。

任务结束时日志里也会留一行汇总：

```
文件统计：视频 下载 12 / 跳过 8；图集 下载 5 / 跳过 3；音乐 下载 2 / 跳过 0
```

## 五、去重优化（需求 4）

### 5.1 内核原本的行为

内核的去重发生在 `Downloader.download_video` / `download_image` 内部，
即**已经拿到作品详情之后**才判断是否下载文件。

对「批量下载链接作品」模式而言，这意味着即使 200 条链接全部下载过，
程序仍会发起 **200 次详情接口请求**，只是跳过了文件下载。

### 5.2 本项目的增强

| 开关 | 行为 |
| --- | --- |
| **下载前预过滤已下载作品**（默认开） | 在发起详情请求**之前**，用一条批量 SQL（`SELECT ID FROM download_data WHERE ID IN (...)`，每批 400 个）比对下载记录，命中即剔除，完全无网络流量 |
| **输出跳过明细日志**（默认开） | 逐条打印被跳过的作品 ID，便于核对 |
| **严格校验本地文件**（默认关） | 下载记录存在但磁盘文件缺失时（手工删除、跨盘迁移、异常中断），把该 ID 判为记录失效并重新下载。需要扫描一次保存目录，文件量极大时会增加启动耗时 |
| **启用下载记录**（默认开） | 对应内核 `Record` 开关；关闭后全部去重逻辑失效 |

账号 / 合集模式同样受益：内核在解析出完整作品列表后会调用
`download_detail_batch`，本外壳对该实例方法做了包装，在进入下载流程前先剔除已下载作品。

### 5.3 实测数据

**（a）预过滤本身的开销** —— 使用真实数据库中的 30,172 条下载记录：

| 场景 | 传入条数 | 命中跳过 | 待处理 | 耗时 |
| --- | --- | --- | --- | --- |
| 全部已下载 | 30,172 | 30,172 | 0 | **113 ms** |
| 一半已下载 | 30,172 | 15,086 | 15,086 | 90 ms |
| 全部未下载 | 15,086 | 0 | 15,086 | 30 ms |

按平均每个详情请求 0.5 s 估算，「全部已下载」场景下相当于省下约 **250 分钟**等待时间。

**（b）实网对照实验**（真实 Cookie + 真实账号，`tests/live_dedup_test.py`）：

| 阶段 | 媒体请求次数 | 说明 |
| --- | --- | --- |
| 阶段 1（记录为空） | 12 次 | 正常采集并逐个请求媒体文件 |
| 阶段 3（作品已记录） | **0 次** | 预过滤全部命中，内核完全未发起媒体请求 |

阶段 3 日志：

```
[去重] 预过滤：账号/合集列表共 9 个作品，跳过 9 个已下载作品，实际需要下载 0 个。
[去重] 本次列表中的作品均已下载，跳过下载阶段。
```

## 六、反爬虫增强（需求 5）

全部增强集中在「反爬虫增强」板块，由 **启用反爬虫增强** 总开关控制；
关闭后完全沿用内核默认策略。

| 参数 | 作用 | 内核默认 | 增强后的行为 |
| --- | --- | --- | --- |
| 请求平均间隔 | 两次数据请求之间的平均等待 | 6.0 s | 可调，按对数正态分布抖动 |
| 间隔抖动系数 σ | 间隔随机性强度 | 0.5 | 可调；σ=0 即固定间隔 |
| 间隔下限 / 上限 | 抖动结果的硬性边界 | 1.5 / 33.3 s | 可调，防止过密或长时间停滞 |
| 文件并发下载数 | 同时下载的文件任务数 | 4 | 可调 1–16，避免并发过高触发风控 |
| **指纹轮换** | 每次任务随机挑选 TLS 指纹与指纹字段 | 固定 `chrome146` | 从指纹池随机取，并保证 TLS 指纹 / UA / 浏览器版本 / 平台 / 系统版本**相互自洽** |
| 指纹池 | 参与轮换的浏览器族 | — | Chrome / Edge / Safari / Firefox，运行时枚举 `curl_cffi` 实际支持的版本 |
| **退避重试** | 失败后等待时间的增长方式 | 固定随机等待 | 指数退避：`基数 × 倍数^(n-1)`，受上限约束 |
| **批次休眠** | 批量模式下主动休眠 | 每 10 个休 300 s（硬编码） | 可配置 N 与时长，0 表示禁用 |
| 作品间额外间隔 | 每个作品处理完后的额外等待 | 无 | 可配置 |

### 6.1 实现方式（非侵入）

| 能力 | 落点 |
| --- | --- |
| 请求节流 | 替换 `src.custom.function.get_wait_time` |
| 退避重试 | 替换 `src.tools.retry.Retry.retry` / `retry_lite` |
| 下载并发 | 替换 `src.downloader.download.Downloader.semaphore` |
| 批次休眠 | 替换 `src.application.main_terminal.suspend` |
| 指纹轮换 | 构造内核参数前写入一套自洽的 `browser_info` |

> 重试装饰器在模块导入时完成绑定，因此补丁的安装顺序是
> **先装补丁、再导入内核业务模块**，这一点在 `engine.py` 中有显式注释保证。

### 6.2 指纹自洽性（重要）

`curl_cffi` 提供的指纹枚举里混有移动端与命名不规范的取值
（`chrome99_android`、`safari180_ios`、`safari17_0`、`chrome133a`、`safari2601` 等）。
直接使用这些值会产生**自相矛盾的画像**，例如「声称 macOS 却使用 Android 指纹」，
反而更容易被识别为异常流量。

因此本项目按浏览器族用正则筛选，并显式推导版本号：

```
Mac + Chrome   → impersonate=chrome146, platform=MacIntel, os=Mac OS 10.15.7, Chrome/146.0.0.0
Windows + Edge → impersonate=edge101,  platform=Win32,    os=Windows 10,     Edg/101.0.0.0
Mac + Safari   → impersonate=safari184, platform=MacIntel, os=Mac OS 10.15.7, Version/18.4
```

这样做是因为抖音的 `a_bogus` 签名会使用这些字段，若 TLS 指纹与 UA 版本不一致，
签名与传输层就会互相矛盾。

> TikTok 平台**只轮换 Blink 内核族（Chrome / Edge）**：其请求参数内嵌完整 UA 串、
> `browser_name` 固定为 `Mozilla`，改用 WebKit / Gecko 的 UA 结构会偏离内核预期。

## 七、上游缺陷修复：昵称变更后的改名逻辑

### 7.1 上游的设计意图

内核用 SQLite 的 `mapping_data(ID, NAME, MARK)` 表记住每个账号 / 合集上次的
昵称与标记。每次处理时对比「表里的旧值」与「本次接口返回的新值」，
如果变了，就把历史文件夹和作品文件名里的旧值替换成新值
（`src/manager/cache.py::Cache`）。

这个机制**只在 `name_format` 勾选了「账号昵称」或「自定义标记」时才会启用**
（由 `TikTok.__init__` 里两个布尔值控制）。

### 7.2 实测发现的缺陷

用真实 `Database` + `Cache` 复现（`tests/cache_rename_test.py`），
在**默认配置**下（`name_format` 含昵称、未设置自定义标记）：

```
FileNotFoundError: [WinError 3] 系统找不到指定的路径: ...\UID123__发布作品
```

根因是两处目录定位不一致：

| 位置 | 拼出的目录名 |
| --- | --- |
| `__check_file()` 判断目录是否存在 | `{前缀}{ID}_{mark or name}_{后缀}` ← 标记为空时回退昵称 |
| `__scan_file()` 实际去遍历的目录 | `{前缀}{ID}_{mark}_{后缀}` ← 原样用标记，为空时得到 `UID123__发布作品` |

于是 `iterdir()` 抛 `FileNotFoundError`。由于异常发生在
`update_mapping_data` 之前，**记录也不会被更新**，导致该账号每次运行都报同样的错；
异常还会一路上抛，中断这个账号的整个处理流程。

另外两个次要问题：

- `__batch_rename()` 用的是 `break` 而不是 `continue`。`iterdir()` 顺序不确定，
  只要第一个文件不含旧值，后面的文件就全都不会被改名。
- 旧值为空字符串时 `str.replace("", new, 1)` 会把新值**插到文件名最前面**。
- 昵称变化时上游**只改文件名、不改文件夹名**，而下载阶段
  `Downloader.storage_folder()` 会按新昵称 `mkdir`，于是同一账号会分裂出
  「旧昵称文件夹（内含已按新昵称改名的文件）」和「新昵称空文件夹」两份目录。
  在既有素材目录里能看到大量同 UID 多昵称的文件夹，
  （如 `UID102734050605_大潘_发布作品` / `_东方超模_` / `_优优_` / `_优优爱健身_`）
  与此行为一致。

### 7.3 本项目的处理

`app/upstream_fixes.py` 在运行时替换 `Cache` 的三个私有方法（不改源码）：

1. **目录定位加固**：依次尝试「标记目录 → 昵称目录 → 模糊匹配 `{前缀}{ID}_*_{后缀}`」，
   取第一个真实存在的，彻底消除 `FileNotFoundError`。
2. **改名遍历全部匹配项**：`break` 改为 `continue`，并在旧值为空时跳过。
3. **可选同步重命名账号文件夹**：昵称变化时把账号文件夹一并改名，
   避免出现「旧文件夹 + 新空文件夹」的重复目录。可用
   「昵称变更时同步重命名账号文件夹」开关关闭。

对应界面开关位于「文件命名与保存位置」板块：

- `修复昵称变更改名缺陷`（默认开）
- `昵称变更时同步重命名账号文件夹`（默认开）

### 7.4 修复效果（实测对照）

| 场景 | 上游原始行为 | 启用修复后 |
| --- | --- | --- |
| 仅昵称变化 | 抛 `FileNotFoundError`，0 个文件改名，记录未更新 | 文件夹改为 `UID123_新昵称_发布作品`，3/3 文件改名，记录更新，无重复目录 |
| 同上 + `folder_mode=True` | 同样抛异常 | 文件夹与作品子文件夹均完成改名 |
| 仅标记变化 | 文件夹改名成功（该路径上游本身可用） | 保持不变，行为一致 |
| `name_format` 不含昵称 | 不改名（符合预期） | 保持一致 |
| 关闭修复开关 | — | 行为与上游完全一致 |

### 打包做了什么

| 步骤 | 说明 |
| --- | --- |
| 清理 `__pycache__` | 避免把 `.pyc` 当资源塞进包里 |

## 十一、常见问题

**Q：提示「Cookie 未登录」？**
A：Cookie 缺少 `sessionid_ss`（抖音）或 `sessionid`（TikTok）。重新从浏览器复制完整
Cookie，点击「校验登录状态」确认。也可以点「导入内核配置」从旧配置里直接导入。

**Q：TikTok 一直超时？**
A：TikTok 通常必须配置代理。在 TikTok 分页的「网络请求」中填写代理地址。

**Q：日志里出现「[交互请求已自动跳过]」？**
A：内核某些分支需要终端交互（例如直播清晰度选择）。图形界面无法交互，
程序会自动安全跳过（不会卡住）。直播录制请填写「直播清晰度」参数。

**Q：界面卡住不动？**
A：采集全部在后台线程执行。若长时间无输出，多为网络超时或正在退避重试，
可在日志区确认；也可先「停止」再调整「请求平均间隔」。

**Q：为什么 txt 文件里的 `#博主昵称` 行没有被处理？**
A：这是有意设计的。程序只处理能解析出链接的行；
形如 `#昵称` 的注释行或说明文字会被忽略，避免产生大量无效请求。
如果确实需要直接填写不带域名的标识符（如 sec_user_id），程序会保留这类裸标识符。

**Q：博主改了昵称，历史文件夹和文件名会自动更新吗？**
A：会，但有一个前提：`name_format` 必须勾选了「账号昵称」（默认已勾选）。
改名由内核的 `mapping_data` 缓存驱动 —— 处理账号时对比上次记录的昵称，
发现变化就替换文件名里的旧昵称；勾选「昵称变更时同步重命名账号文件夹」
后账号文件夹名也会一起更新。

需要注意：内核原始实现在默认配置下这段逻辑会抛 `FileNotFoundError`
（详见第七节），所以请保持「修复昵称变更改名缺陷」为开启状态。
如果你的素材目录里已经出现了同一 UID 多个昵称文件夹，那是上游
「只改文件名、不改文件夹名 + 按新昵称新建目录」造成的，本项目的新设置可避免继续产生。

**Q：日志出现「未能解析出任何作品 ID」，怎么排查？**
A：九成是**下载类型选错**。用 txt 读账号列表时，文件里是
`douyin.com/user/...` 这类**账号主页链接**，必须把「下载类型」选成
**批量下载账号作品**；「批量下载链接作品」只认含 19 位作品 ID 的作品链接。

程序会在启动前自动识别并给出提示，也可以看运行日志里的
`链接类型检查：共 N 条，账号主页链接 N 条` 一行来确认。详见第 4.6 节。

**Q：为什么之前跑一次要十几分钟？**
A：那是内核逐条解析链接的耗时（每条一次请求 + 反爬间隔）。现已优化为
**只对短链发请求**，完整链接直接提取作品 ID；短链解析另有进度与预估耗时提示。

**Q：双击「启动.bat」一闪而过（闪退）怎么办？**
A：该脚本已按 cmd 的解析要求重写（GBK 编码 + CRLF 换行、不使用 `goto`、
不在代码块内使用 `&` 转义、不调用 `chcp`），并把报错保留在窗口里（末尾有 `pause`）。

之前闪退的原因有三处叠加，都属 cmd 批处理的解析陷阱：

1. 文件以 **LF** 换行保存 —— cmd 的 `goto` / 标签 / 代码块解析依赖 CRLF；
2. 代码块内写了 `^&^&` —— 括号块中 `&` 的转义行为与行内不同，会打断代码块；
3. `chcp 65001` + UTF-8 中文 —— 运行中切换代码页会打乱按字节偏移重读的解析。

如果仍然闪退，请手动确认：

- `.venv\Scripts\python.exe` 是否存在（不存在则会回退用系统 `python`）；
- 直接运行 `.venv\Scripts\python.exe run.py` 看是否报错（命令行版正常说明是脚本问题）。

**Q：勾选框和文件名预览在哪里？**
A：勾选态显示为「绿色方块 + 白色对勾」，未勾选为白底灰边。
「文件命名与保存位置」板块的「文件名组成」下方会**实时生成参考文件名**，
勾选元素或改分隔符时立即刷新，详见第 4.4 节。

**Q：怎么彻底停用某项优化？**
A：在「反爬虫增强」里关闭总开关，在「去重优化」里关闭「下载前预过滤已下载作品」，
即完全回到内核原始行为。
